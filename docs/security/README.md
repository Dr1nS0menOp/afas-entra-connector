# Security assurance

How afas-entra-sync is checked against public security standards, and how you can verify
the claims yourself. Last reviewed 2026-11-01 (version 0.10.0).

| Framework | What it covers | Status | Evidence |
| --- | --- | --- | --- |
| [OWASP ASVS 5.0.0](https://owasp.org/www-project-application-security-verification-standard/), Level 2 | The application: input, output, authentication, sessions, access, cryptography, TLS, configuration, data, logging | Self-assessed: all 253 Level 1 and 2 requirements assessed; 136 met, 18 met with a documented deployment condition, 99 not applicable, 0 not met | [asvs-5.0-L2.csv](asvs-5.0-L2.csv), generated by [asvs_assessment.py](asvs_assessment.py) and verified in CI |
| [OpenSSF Best Practices](https://www.bestpractices.dev/) (passing) | The project: licence, change control, reporting, tests, analysis, delivery | All criteria the project controls are met; the rest are met once the repository is public | [OPENSSF-BEST-PRACTICES.md](OPENSSF-BEST-PRACTICES.md) |
| [OpenSSF Scorecard](https://scorecard.dev/) | Automated checks of the repository and its supply chain | Runs in CI and publishes its score once the repository is on GitHub | `.github/workflows/scorecard.yml` |
| Build provenance ([SLSA](https://slsa.dev/) build level 2) | Who built a release, from which commit | Every release is built and signed by GitHub Actions | `.github/workflows/release.yml`; verify with `gh attestation verify` |

A self-assessment is not a certification. For an independent ASVS verification, give a
tester this directory: every requirement points to the code, test or document that
supports it.

## How to verify

```
cargo test                        # 238 tests, including the security tests named in the CSV
cargo clippy --all-targets -- -D warnings
cargo deny check                  # known vulnerabilities, licences, sources (deny.toml)
cargo audit                       # RustSec advisory database
cargo +nightly fuzz run <target>  # fuzz/: afas_response, config, small_parsers, gui_request
python3 docs/security/asvs_assessment.py --check   # ASVS evidence current and resolving
for d in docs/security/evidence/*/; do (cd "$d" && sha256sum -c SHA256SUMS); done
gh attestation verify afas-entra-sync-<version>-linux-x86_64.tar.gz --repo <owner>/afas-entra-sync
```

The latest results are in [SCAN-REPORT.md](SCAN-REPORT.md); the raw tool output, with
checksums, in [evidence/](evidence/2026-11-01-v0.10.0/MANIFEST.md) (0.10.0) and [the 0.9.3 run](evidence/2026-11-01/MANIFEST.md).

## How the evidence stays true

- `asvs-5.0-L2.csv` is generated by `asvs_assessment.py` from the **official** OWASP list,
  fetched at the `v5.0.0_release` tag and verified by SHA-256. CI (`ci.yml`, job
  "Security evidence") regenerates it on every push and fails if the committed file
  differs.
- The same job fails when any evidence or security document points to a file, test or
  code symbol that no longer exists, or to a broken link. Renaming a test that proves a
  requirement breaks the build until the evidence is updated.
- Stored scan output is checked against its `SHA256SUMS`.
- The scans themselves (cargo-deny, cargo-audit, secrets, zizmor, shellcheck, CodeQL,
  Scorecard, fuzzing) run in CI, so each commit has fresh results in the Actions and
  Security tabs.

## Deployment conditions

The 18 "Met (deployment)" requirements hold when the program is deployed as documented.
These are the conditions; tick them off when you install:

- [ ] **Sign-in strength**: local mode needs SSH as the service user to read the login link;
  require keys or MFA on SSH. Proxy mode: require MFA in Authentik. (V6.3.3, V6.8.4)
- [ ] **TLS to the GUI**: local mode is loopback only, reached through an SSH tunnel. Proxy
  mode: run Traefik on the same host, or encrypt the hop (WireGuard, IPsec) when Traefik
  runs elsewhere. Traefik serves a publicly trusted certificate and redirects HTTP to
  HTTPS. (V3.4.1, V4.1.2, V4.2.1, V12.2.2, V12.3.1, V12.3.3, V12.3.4)
- [ ] **Proxy header**: Traefik with Authentik forward-auth sets `X-authentik-username` and
  overwrites any value from the client. (V4.1.3)
- [ ] **Own host name** for the GUI behind the proxy. (V3.5.4)
- [ ] **Sessions behind the proxy**: set session lifetime and user deactivation in
  Authentik. (V7.1.3, V7.4.2, V7.6.1)
- [ ] **Secrets** come from your secret store (Ansible Vault, Semaphore secrets) into the
  0600 files or environment variables. (V13.3.1)
- [ ] **Time** synchronised with NTP. (V16.2.2)
- [ ] **Logs** forwarded to a separate system (for example Graylog). (V16.4.2, V16.4.3)

## Sign-in and sessions (GUI)

The GUI is off by default. When on, it has one of two sign-in pathways, never both:

**Local mode** (listens on loopback only):

- `serve` writes a login link to `<state.dir>/gui-login-url` (0600, service user). Reading
  it requires SSH access to the server as that user.
- The link carries 256 random bits, works **once** and expires after **15 minutes**. After
  use or expiry a new link replaces it in the same file. It is not a session token: opening
  it starts a new session and redirects, so the code leaves the address bar at once, and
  `Referrer-Policy: no-referrer` keeps it out of any Referer header.
- Each sign-in gets a new 256-bit session id in the cookie `__Host-afas_gui_session`
  (`Secure; HttpOnly; SameSite=Strict; Path=/`). Sessions end after **30 minutes**
  without activity and after **8 hours** in any case; at most **20** run at once (the
  oldest ends first). "Sign out" ends the session and sends `Clear-Site-Data`; "Sign out
  all sessions" on the GUI page ends every session; a restart ends them too.
- Guessing is infeasible (256 bits, one use), so there is no lock-out to abuse. Refused
  links, sessions and form tokens are written to `audit.log`.

**Proxy mode** (`--trusted-proxy`): only connections from the configured proxy address
are accepted, with the user name from Authentik. Authentik owns sign-in, MFA and session
lifetime.

Every change is a POST with a form token, on top of `SameSite=Strict` and a Host header
check. Other methods than GET and POST are refused.

## Authorization

One role: administrator. Who reaches the GUI decides who administers it: SSH access in
local mode, the Authentik policy in proxy mode. `--read-only` makes the whole server
read-only. Some settings are locked to the config file whoever signs in: addresses,
secrets, the TLS policy, module identities and the GUI switch.

## Communications

| Direction | Endpoint | Purpose | Protection |
| --- | --- | --- | --- |
| Out | AFAS Profit REST (`*.rest.afas.online`) | Read employees | TLS 1.3, AFAS token |
| Out | `login.microsoftonline.com` | Tokens | TLS 1.3, certificate (client assertion) |
| Out | `graph.microsoft.com` | Upload, provisioning logs, modules | TLS 1.3, bearer token; only the configured host |
| Out | Webhook URL (optional) | Events for ITSM | TLS 1.3, HMAC signature |
| In | GUI (optional) | Administration | Loopback or trusted proxy; see above |

All addresses are in the config file and locked for the GUI. Redirects are not followed;
paging links to another host are refused.

## Availability

Resource-heavy functions and how they are bounded:

| Function | Bound |
| --- | --- |
| A sync run | One at a time (lock file); `max_calls_per_run`; Microsoft pacing and Retry-After (capped) |
| Reading AFAS | Response ≤ 128 MiB, ≤ 1,000,000 rows |
| Provisioning logs | Response ≤ 32 MiB, ≤ 200 pages |
| Graph calls in modules | Responses ≤ 32 MiB each (a page of up to 999 users), ≤ 1,000 pages; per-module maximum changes per run |
| GUI requests | Body ≤ 64 KiB; one run at a time; loopback or proxy only |
| Webhook | ≤ `max_per_run` deliveries per run; queue ≤ 10,000 events |
